Subscribe with `graph.on(name, handler)`, which returns the function that unsubscribes. In React, use the matching prop of `<Graph>` or `useGraphEvent`. Payloads take `M`, the union of the marks of the definition, which types their targets: `mountGraph` and `<Graph>` pass it for you.

## Subscribe with a signal

```ts
on<K extends GraphEventName>(
  name: K,
  handler: GraphEventHandler<K, M>,
  options?: GraphEventOptions,
): () => void
```

The third argument takes a `signal`: the handler is removed when it aborts, as with `addEventListener`. A signal already aborted subscribes nothing. Once the graph is destroyed, `on` subscribes nothing and returns a function that does nothing.

```ts
const controller = new AbortController()
graph.on('click', select, { signal: controller.signal })
graph.on('pointerenter', show, { signal: controller.signal })
controller.abort()
```

## Targets

```ts
type GraphTarget<M extends Mark = Mark> =
  M extends NodeMark<infer T, infer N, MarkLayer>
    ? NodeTarget<T, N>
    : M extends EdgeMark<infer T, infer N, MarkLayer>
      ? EdgeTarget<T, N>
      : M extends ShapeMark<infer T, infer N, MarkLayer>
        ? ShapeTarget<T, N>
        : NodeTarget | EdgeTarget | ShapeTarget
```

`GraphTarget<M>` is a `NodeTarget`, an `EdgeTarget` or a `ShapeTarget` for each mark of `M`, the union of the marks of the definition. `datum` is the item from your data, typed by its mark, and `mark` is the `name` of that mark, `undefined` without one. Narrow on `kind`, then on `mark` when several marks of one kind carry different types: see [TypeScript](/docs/typescript). Without a [shape mark](/docs/shapes) in `M`, no target is a shape. Without `M`, `datum` is `unknown` and `kind` can be any of the three.

An edge drawn for several edges, between [folded groups](/docs/groups) or [merged](/docs/transformations#merge-parallel-edges) by `merge`, carries `aggregate`, with the keys and data of every merged edge, split by direction; `key` and `datum` are those of the first. With [`halves`](/docs/transformations#one-direction-per-half), the half of a two-way line under the pointer sets `direction`, and `key` and `datum` are those of the first edge of that direction.

`endpoints` holds the keys of the two ends of an edge as drawn: an end hidden in a folded group is the key of that group. To read the item of an end, pass it to `graph.datumOf({ kind: 'node', key })`.

- `point` is in screen pixels relative to the graph element, `world` in world units.
- `pointermove` carries a `GraphPointerEvent`, at most once per frame, with the element under the pointer or `null` over empty space. During a drag, its target is the dragged node. The graph listens to the pointer for it only while a handler is subscribed.
- `selection` is the whole selection after the change, in the order keys joined it. It has `shapes` only when the definition has a [shape mark](/docs/shapes#selecting-and-hovering).
- `origin` is `'user'` when a gesture, the wheel, the keyboard or edge scrolling moved the view, and `'api'` when code did: `graph.view`, `update({ view })`, automatic framing or the keyboard focus set from code.
- `keys` lists every node moved by the drag: the whole selection when the dragged node is selected, and the nodes inside a dragged group.
- `folded` lists the keys of every folded group after the change.
- `zoomhint` fires in `'page'` wheel mode for each wheel event left to the page. `key` is the key to hold to zoom: `'Meta'` (Cmd) on Apple systems, `'Control'` elsewhere. Show your own hint: the graph shows none. See [Wheel and trackpad](/docs/interaction#wheel-and-trackpad).
- `lens` is the lens after the change, `null` when it hides. See [Lens](/docs/lens).
- `window` is the time window after the change, in milliseconds, `null` when every element shows. See [Time](/docs/time).
- `hidden` lists the names of the hidden layers after the change, in the order of the marks. See [Multilayer graphs](/docs/multilayer).
- `issues` lists the problems present in the data once a data change is applied, as [`graph.issues()`](/docs/api/graph-instance#issues) returns them, empty once they are all fixed. `issueschange` fires only when that list changes. A handler subscribed after the first data arrived reads the current list with `graph.issues()`.
- `loadingchange` carries the new `data` of the store: `loading` is `true` while a live source of the definition is loading, and `failed` lists the sources whose load failed. It fires once the change is applied, with the data the sources delivered. See [Loading](/docs/data#loading).
- `positions` holds the target positions. Moves that come from your data do not emit `positionchange`.
- With the origin `'layout'`, `positions` holds every node the run moved. A stopped run emits nothing.
- `name` is the name of the layout, `'force'` for [`force()`](/docs/api/force). `completed` is `false` when the run was stopped or replaced.

## Order

`click` fires before the default selection, so a handler sees the selection as it was. `selectionchange` and `viewchange` fire on every change, from the user or from code. In controlled mode, `selectionchange` fires when a new `selection` is applied, and `onSelectionChange` on `<Graph>` receives requests, in the same payload, instead of events. `foldchange` and `onFoldChange` follow the same rule with `folded`, `viewchange` and `onViewChange` with `view`, `timechange` and `onTimeChange` with `time`, and `layerchange` and `onLayerChange` with `hiddenLayers`.

A `doubleclick` on a group folds or unfolds it after the handlers run, unless one calls `originalEvent.preventDefault()`.

At the end of a layout run, `positionchange` fires before `layoutend`. Nodes that arrive during a run join it without a new `layoutstart`, and a run replaced by another ends with `completed: false` before the next `layoutstart`.

## Errors in handlers

Handlers run one after the other, as the listeners of a DOM element do. A handler that throws stops neither the next handlers of the event nor the graph: a click still selects, a layout run still settles and the frame is still drawn. Its error goes to [`reportError`](https://developer.mozilla.org/docs/Web/API/Window/reportError), which reports it as an uncaught error, with an `error` event on `window` and a line in the console. Where `reportError` is missing, the error is thrown again from a timer, once the graph is done.

The same rule holds for the subscribers of `graph.store`, of the [legend](/docs/api/legend) store and of the [timeline](/docs/api/timeline) store, and for the callbacks of the controlled modes: `onSelectionChange`, `onFoldChange`, `onViewChange`, `onTimeChange` and `onLayerChange`.

```ts
graph.on('click', () => {
  throw new Error('broken handler')
})
graph.on('click', ({ target }) => console.log(target))
```

Here the second handler still logs, and the click still selects.

A handler removed during an event, by itself or by an earlier handler, is not called for that event, and one added during it waits for the next. A handler can destroy the graph: the handlers left for the event are not called, and the graph changes nothing after it, so a click whose handler destroys the graph selects nothing.
