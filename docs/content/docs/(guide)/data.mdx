## Two kinds of data

A mark reads one of two things:

- **An iterable**, such as an array or the result of a query. Every new definition is reconciled by key: only the differences reach the screen, and positions stay where they are.
- **A live source**: any object with a `subscribeChanges(callback, options)` method. Its inserts, updates and deletes are applied in batches, once per frame. A TanStack DB collection or live query is a live source as is, with no adapter.

```ts
import type { LiveSource } from '@bruno00o/graph'

const source: LiveSource<Item> = {
  subscribeChanges(callback, options) {
    if (options?.includeInitialState) callback(initialRows.map((row) => ({ type: 'insert', key: row.id, value: row })))
    const stop = listen((change) => callback([change]))
    return { unsubscribe: stop }
  },
}
```

A source is recognized by its `subscribeChanges` method before anything else, so a collection that is also iterable is still read as live.

The graph holds a live source to this contract:

- It subscribes with `includeInitialState: true`, so the items already there come first, as inserts.
- The key of an element is the `key` of its change: a mark of a live source takes no `key` option. A change whose key is neither a string nor a finite number is skipped and reported as a `missing-key` problem, until a delete with the same key withdraws it.
- An insert or an update sets the item under its key; a delete removes the element with that key. A batch without changes is ignored.
- Everything else, edge ends included, is read from the item through the options of the mark.
- A source may tell how far it has loaded with a `status` and an `on` method: see [loading](#loading). Without them, it is loaded as soon as it is subscribed.

The result of a Cypher query is read into two arrays by [`cypherGraph`](/docs/cypher), and a GraphML, GEXF, JSON Graph Format or CSV file by the readers of [file formats](/docs/file-formats).

Examples: [a live source of your own](/examples/live-source) streams nodes and edges without TanStack DB, and [a collection as the source](/examples/collection-source) reads two TanStack DB collections.

## Loading

A live source may load its items over time: a collection fetching from a server, a query waiting for an answer. It says so with two optional members, which a TanStack DB collection, a live query, `subset` and the sources of `createExploration` already have:

- `status`: `'loading'`, `'loadingSubset'` or `'idle'` while its first load runs, `'error'` or `'crashed'` when that load failed, `'ready'`, or any other value, once loaded.
- `on('status:change', listener)`: calls `listener` when `status` changes, and returns a function that stops it.

The subscription that `subscribeChanges` returns may have the same two members, for what that one subscription asked for, such as the rows of a `where`. The graph is loading while the source or its subscription is.

```ts
const source: LiveSource<Item> = {
  get status() {
    return loaded ? 'ready' : 'loading'
  },
  on(_event, listener) {
    readyListeners.add(listener)
    return () => readyListeners.delete(listener)
  },
  subscribeChanges(callback, options) {
    if (options?.includeInitialState) callback(rowsSoFar.map((row) => ({ type: 'insert', key: row.id, value: row })))
    const stop = listen((change) => callback([change]))
    return { unsubscribe: stop }
  },
}
```

The graph reads three things from its sources, in the store and by events:

- `data.loading` in the store is `true` while a live source of the current definition is loading. A new definition with sources that load goes back to `true`. Array data and sources without a `status` are always loaded.
- `data.failed` lists the sources whose load failed, in mark order. The graph keeps drawing what they delivered and never throws; a source leaves the list once its `status` recovers.
- `loadingchange` fires when either changes, with the new `data`, and `await graph.loaded()` resolves once nothing loads and what the sources delivered is applied. It resolves at once when nothing loads, and after a failure too. To wait for the drawing as well, `await graph.drawn()` next.

The graph draws no loading indicator of its own: show yours from `data`.

```ts tab="Vanilla" tab-group="framework"
const overlay = document.querySelector<HTMLElement>('.loading-overlay')

graph.store.subscribe(({ data }) => {
  overlay.hidden = !data.loading
})
```

```tsx tab="React" tab-group="framework"
import { useGraphState } from '@bruno00o/graph/react'

function LoadingOverlay() {
  const data = useGraphState((state) => state.data)
  if (data.failed.length > 0) return <p role="alert">Some data could not be loaded.</p>
  return data.loading ? <p role="status">Loading the data</p> : null
}
```

### Layout and fit on complete data

While a source loads, its batches are drawn as they come, placed near their neighbors or on a spiral. The automatic layout over every node and the automatic fit of the view wait for the data: they run once every source has loaded or failed, so a graph that arrives in several batches gets the same layout as if it had come at once, and the view frames all of it. Nodes that arrive later, once the first layout has run, are placed by the layout as before.

The wait is bounded by `waitForData` of `defineGraph`: 10 seconds by default, counted from the first nodes. When the time is up, the layout and the fit run on what is there, and later batches are placed as they come. `true` waits for as long as the sources load, `false` or 0 does not wait at all.

```ts
const definition = defineGraph({ marks, layout: force(), waitForData: 30_000 })
```

The [loading overlay](/examples/loading-overlay) example loads a collection in three delayed batches behind an overlay of its own, then lays out the complete graph once.

## Keys

Keys are strings or numbers.

- **Nodes.** By default the key is the `id` field. When your data has no `id`, the `key` option is required: a field name or a function.
- **Edges.** Same rule for the edge key. `source` and `target` take a field holding a node key, or a function.
- **Live sources** carry the key in each change, and their marks take no `key` option.

```ts
type Row = { code: number; name: string }
type Pair = { start: number; end: number; kind: string }

declare const rows: Row[]
declare const pairs: Pair[]

nodes(rows, { key: 'code', label: 'name' })
edges(pairs, {
  key: (pair) => `${pair.kind}:${pair.start}:${pair.end}`,
  source: 'start',
  target: 'end',
})
```

Node keys are unique across all node marks. When two items share a key, the first one wins, in mark order then data order, and the others are skipped. Each skipped key is reported: see [problems in the data](#problems-in-the-data).

## Edges that arrive first

An edge whose ends are not both present yet waits. It appears as soon as its second end arrives, which suits sources that load nodes and edges separately. `graph.count().pending` tells how many edges wait.

## Problems in the data

The graph never stops on bad data: it draws around each problem and lists it. `graph.issues()` returns the problems present now, and `issueschange` fires when they change.

| `type` | Problem | What the graph does |
| --- | --- | --- |
| `missing-key` | An item, or a change of a live source, whose key is neither a string nor a finite number | Skips the item |
| `duplicate-key` | A key held by more than one node, or more than one edge | Keeps the first item, in mark order then data order |
| `missing-parent` | A node whose `parent` names no node | Leaves the node at the top level until that node comes |
| `parent-cycle` | A node whose `parent` would make it contain itself | Leaves the node at the top level |
| `missing-carrier` | An edge whose `supportedBy` names no edge | Ignores that carrier |

```ts tab="Vanilla" tab-group="framework"
graph.on('issueschange', ({ issues }) => {
  banner.hidden = issues.length === 0
  banner.textContent = issues.map((issue) => issue.type).join(', ')
})
```

```tsx tab="React" tab-group="framework"
const [issues, setIssues] = useState<readonly GraphIssue[]>([])

<Graph definition={definition} ariaLabel="Sample graph" onIssuesChange={({ issues }) => setIssues(issues)} />
```

A problem goes away once the data no longer holds it: remove the second item of a key and its `duplicate-key` goes, add the missing parent and its `missing-parent` goes. The list is therefore a state, not a log, and the same array comes back until it changes. An edge waiting for an end is not a problem.

In development, each data change that brings new problems logs one console warning that counts them by type; read the details with `graph.issues()`. The [devtools](/docs/devtools) panel lists them too, including those found before it opened.

The [problems in the data](/examples/data-issues) example lists the problems of its data as you fix and break it.

## Update the data

Never change an array in place: the graph does not read the same mark object twice. Build a new array and a new definition instead.

```ts tab="Vanilla" tab-group="framework"
items = [...items, { id: 'n5', label: 'Node 5', group: 'D', weight: 3 }]
graph.update({ definition: defineGraph({ marks: [edges(links, linkOptions), nodes(items, itemOptions)] }) })
```

```tsx tab="React" tab-group="framework"
const definition = useMemo(
  () => defineGraph({ marks: [edges(links, linkOptions), nodes(items, itemOptions)] }),
  [items, links],
)
return <Graph definition={definition} ariaLabel="Sample graph" />
```

When a mark keeps its place and its options are equal, only the items that changed are rewritten. When options change, every item of that mark is restyled. Options are compared by content: plain objects and arrays written inline, such as `label: { text: 'name', size: 14 }` or `ends`, are equal when their values are, and a definition rebuilt on every render rewrites nothing. Functions compare by identity: declare them once, outside the component or in a `useMemo`, or each render restyles every item of the mark.

With a live source, there is nothing to update: changes arrive through the subscription.

Examples: [changing data](/examples/changing-data) replaces the array on a timer, [expand on double-click](/examples/expand-on-double-click) adds the neighbors of a node, [edges in batches](/examples/edges-in-batches) adds 50,000 edges at a time, and [positions from data](/examples/positions-from-data) moves nodes by their `x` and `y`.

## Removed elements

An element removed from the data leaves the selection and the hover. Your own states keep its key, and their style applies again if the element comes back.
