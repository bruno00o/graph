## The view

The view is a center point in world units and a zoom factor: `{ x, y, zoom }`. At zoom 1, one world unit is one CSS pixel.

```ts
graph.view.get()
graph.view.set({ x: 0, y: 0, zoom: 2 }, { duration: 300 })
graph.on('viewchange', ({ view }) => console.log(view.zoom))
```

## The first view

Without `initialView`, the graph fits all its nodes with a 32 pixel margin as soon as the first data arrives. An empty graph waits for its data, so a collection that fills after mounting is still fitted. Only that first batch is fitted: later data does not move the view.

To start somewhere else, pass `initialView` when you mount.

```ts
mountGraph(container, { definition, ariaLabel: 'Sample graph', initialView: { x: 0, y: 0, zoom: 1 } })
```

## Fit

`fit` frames the given nodes, or every node without keys.

```ts
graph.view.fit()
graph.view.fit(['n1', 'n2', 'n3'], { padding: 64, duration: 400 })
```

`padding` is in screen pixels, 32 by default. A `fit` called before the graph has measured its container waits for that measure.

## Zoom

`zoomBy` multiplies the zoom around the center of the view.

```ts
graph.view.zoomBy(1.5, { duration: 200 })
graph.view.zoomBy(1 / 1.5, { duration: 200 })
```

Animated calls interrupt each other: the last one wins. With `prefers-reduced-motion`, every duration is zero.

How the wheel, a trackpad and fingers move the view is set in the [interaction options](/docs/interaction#wheel-and-trackpad).

## View limits

The `view` of the definition bounds the zoom and the area the view can show. Every move stays within them: gestures, keys, `view.set`, `view.fit`, `view.zoomBy`, `initialView`, and each frame of an animation.

```ts
defineGraph({
  marks,
  view: { minZoom: 0.1, maxZoom: 8, bounds: { margin: 120 } },
})
```

`minZoom` and `maxZoom` are in screen pixels per world unit, 0.001 and 64 by default. `fit` frames as closely as `maxZoom` allows, so fitting a single node does not zoom past it.

`bounds` takes one of two forms:

- A rectangle in world units, `{ minX, minY, maxX, maxY }`: the view cannot show past it, as on a map with an edge.
- `{ margin }`: the box of every node, grown by `margin` screen pixels on each side. The graph cannot be pushed off screen, and you can pan until its edge sits `margin` pixels from the edge of the element.

Where the area is narrower than the view, for example once you zoom out, the rule turns around: the area cannot leave the view, but it can move inside it.

```ts
defineGraph({ marks, view: { bounds: { minX: -1000, minY: -600, maxX: 1000, maxY: 600 } } })
```

Bounds apply when the view moves, when the element is resized and when the definition changes. Data changes do not move the view: with `{ margin }`, nodes that arrive or leave widen or narrow the area at the next move. See [`ViewLimitOptions`](/docs/api/define-graph#view) for the full option list.

## Controlled view

To keep the view in your own state, pass `view` when you mount the graph, with `onViewChange`. The graph then draws the view you give it, as given. Gestures, keys, `view.set`, `fit`, `zoomBy` and every frame of their animations become requests, kept within the view limits: `onViewChange` receives them, at most once per frame and before the frame is drawn. Apply a request with `update({ view })`, change it first, or drop it.

```ts
let view: View = { x: 0, y: 0, zoom: 1 }

const graph = mountGraph(container, {
  definition,
  ariaLabel: 'Sample graph',
  view,
  onViewChange: (event) => {
    view = { ...event.view, y: 0 }
    graph.update({ view })
  },
})
```

Here the application keeps the view on a horizontal line: vertical moves are dropped, the rest goes through.

A view applied inside `onViewChange` is drawn in the same frame, so a controlled view follows the pointer without lag. An application that answers later still gets smooth gestures: each new request starts from the last request it has not answered yet, and a view it applies that matches none of them replaces them all.

The mode is fixed at mount: a graph mounted with `view` stays controlled for its whole life. The first fit does not run in controlled mode, and `viewchange` fires only when an applied view differs from the current one. In React, pass the `view` and `onViewChange` props: see [React](/docs/react#controlled-view).

## Screen and world coordinates

Positions live in world units. To place an HTML overlay over a node, convert its position to screen pixels relative to the graph element.

```ts
const point = graph.positions.get('n1')
if (point) {
  const { x, y } = graph.view.toScreen(point)
  tooltip.style.transform = `translate(${x}px, ${y}px)`
}
```

`toWorld` does the reverse, for example to drop a new node where the user clicked. Pointer events already carry both: `point` in screen pixels and `world` in world units.

The store holds the view, the width and the height of the graph, so overlays can subscribe to them. To keep an element on a node without any code per frame, pin it with [`graph.anchors.set`](/docs/drawing-layers#anchored-html).
