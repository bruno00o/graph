## Add a layout

Pass a layout to `defineGraph`. The force layout comes from its own entry point, `@bruno00o/graph/layouts/force`, so a graph that does not use it carries none of its code.

```ts
import { defineGraph, edges, nodes } from '@bruno00o/graph'
import { force } from '@bruno00o/graph/layouts/force'

const definition = defineGraph({
  marks: [
    edges(links, { source: 'from', target: 'to' }),
    nodes(items, { color: 'group', size: 'weight', label: 'label' }),
  ],
  layout: force({ edgeLength: 60 }),
})
```

Nodes push each other apart, edges pull their ends together like springs, and a light pull toward the center keeps separate components close. A collision force keeps a small gap between nodes. The members of an unfolded [group](/docs/groups) also pull together, and a folded group counts as one node.

The entry point has no peer dependency, and the worker ships inside the package: there is nothing to configure in your bundler.

## Layers

`@bruno00o/graph/layouts` holds layouts that compute their result at once, on the main thread. `layers` draws a directed graph in layers: every edge points from one layer to a later one, in the direction you choose.

<LiveExample slug="layouts" />

```ts
import { layers } from '@bruno00o/graph/layouts'

layers()

layers({ direction: 'right', root: 'start', layerSpacing: 80, nodeSpacing: 16 })
```

- **Layers.** Each node goes on a layer so that its edges point to later layers and stay as short as they can: a node that only feeds deeper ones moves down next to them. `root` puts nodes on the first layer, even when edges lead into them.
- **Cycles.** When edges form a cycle, as few of them as possible are turned around to break it. They are still drawn, pointing back.
- **Order.** The nodes of each layer are sorted to cross as few edges as possible, and each sits close to its neighbors in the layers next to it. Edges are drawn straight. An edge that skips layers holds a place in each layer it crosses, so other nodes tend to keep clear of it.
- **Width.** Nodes are drawn toward their neighbors and edges that skip layers run almost straight, so a dense graph whose edges cross many layers stays about as wide as its busiest layer, with short edges. Graphs with unfolded groups keep their nodes aligned with their neighbors instead, so that each container stays a box.
- **Spacing.** `layerSpacing` is the gap between two layers and `nodeSpacing` the gap between two nodes of a layer, both between node borders: large nodes push their neighbors apart. A [box](/docs/marks#boxes) counts with its width along its layer and its height across, so wide boxes stay close from layer to layer when the direction is down or up. Node labels are left out: give long labels room with a larger gap.
- **Components.** Separate parts of the graph and lone nodes sit side by side, the largest first, wrapped in rows that keep the whole drawing close to a square.
- **Groups.** Unfolded groups share the layers of the rest of the graph, and each one stays a single box on every layer it spans. See [groups in layouts](#groups).

Examples: [layer direction and spacing](/examples/layer-spacing), and [layers from a root, with cycles](/examples/layer-root).

The result is centered on the current center of the nodes it moves. Nodes with `x` and `y` in your data keep their place, and their edges are left out. A graph with 10,000 nodes and 15,000 edges is laid out in a few tens of milliseconds, and one with 50,000 nodes in a few hundred. Edges that skip many layers cost more. Groups add about half: 40 milliseconds instead of 28 for 10,000 nodes in about 100 groups nested three deep, half a second instead of a quarter for 50,000 nodes in 500 groups.

## Grid, rings and radial

The other layouts of `@bruno00o/graph/layouts` take no account of edge direction, and lay out thousands of nodes in a few milliseconds.

```ts
import { grid, radial, rings } from '@bruno00o/graph/layouts'

grid<Item>({ order: (a, b) => a.group.localeCompare(b.group) })

rings({ center: 'hub' })

radial({ root: 'hub' })
```

- **`grid`** lines nodes up in rows, as many columns as rows by default. `order` sorts them, either `'degree'` or a function that compares the data of two nodes.
- **`rings`** puts the first node in the middle and fills rings outward, each ring longer than the last. Nodes come by degree, the busiest first, unless `order` says otherwise. `center` picks the middle node.
- **`radial`** walks the graph from `root` and places each node on the ring of its distance to the root, next to the node it was reached from. Each branch gets a slice of the circle in proportion to its size. Without `root`, it starts from the node with the most edges. Nodes it cannot reach go on an outer ring.

The three are centered on the current center of the nodes they move. Their `spacing` is the gap left between the borders of the largest nodes, as in every layout here; it defaults to the largest diameter, and at least 24. A fixed `center` or `root`, one with `x` and `y` in your data, stays where it is and the others gather around it. On a grid, columns are as wide as the widest [box](/docs/marks#boxes) and rows as tall as the tallest; rings, radial, `force` and `geo` see a box as the circle around it, so boxes never overlap but sit further apart than they would need to side by side.

These layouts, and `layers`, are not incremental: when nodes arrive, every free node is laid out again, so the layers, the grid or the rings stay whole. See [`layers`, `grid`, `rings`, `radial`](/docs/api/layouts) for every option.

Examples: [grid sorted by a field](/examples/sorted-grid), [rings around a center](/examples/ranked-rings), and [radial tree from a root](/examples/radial-tree).

## Geography

`geo` places nodes by their longitude and latitude, with the Web Mercator projection of [map mode](/docs/map), on a graph without a map. Unlike the `longitude` and `latitude` channels of `nodes()`, which pin a node to its place, it then moves apart the nodes that overlap, so every node can be read and clicked.

<LiveExample slug="geo-layout" />

```ts
import { geo } from '@bruno00o/graph/layouts'

geo()

geo<Place>({ longitude: 'lng', latitude: 'lat', order: 'degree' })

geo({ center: { longitude: 2.35, latitude: 48.86 }, scale: 4096 })
```

- **Projection.** `longitude` and `latitude` read the coordinates of each node, the fields of those names by default. The world of a map spans 512 units; `scale` multiplies it, and `center` is the place drawn at the origin.
- **Scale.** By default, the scale comes from the data: the smallest one at which about one place in five would share its spot with another. Data spread over a city or over a continent give a graph of the same size.
- **Spread.** A node that overlaps no other stays exactly at its place. One that would overlap takes the closest free spot, and a crowd of nodes grows into a disk around where it stands. Every node ends at least `spacing` away from the others, fixed nodes included.
- **Same place.** Nodes at the very same coordinates gather around their place: up to six on a ring, more on a spiral, in the internal order or by `order`.
- **No coordinates.** A node without valid coordinates goes next to its placed neighbors, and its own neighbors after it. Nodes with no placed neighbor at all line up in a grid beside the others.

`geo` is not incremental: when nodes arrive, every free node is placed again. Without `scale` and `center`, both follow the data, so new nodes can move the others. Give both to keep positions steady, or to match the camera of a map: see [the same graph with and without a map](/docs/map#with-and-without-a-map). 100,000 nodes, a third of them sharing their place with another, take about 150 milliseconds. See [`geo`](/docs/api/layouts#geo) for every option.

## Groups

Every layout keeps unfolded [groups](/docs/groups) whole, at every level of nesting: when it ends, no container overlaps another container or a node next to it, padding included. A folded group is one node like any other.

<LiveExample slug="nested-groups" />

- **`force`.** The members of a group pull toward its center, `cohesion` sets how hard. Edges between groups pull whole groups toward each other rather than tearing members out. As the layout cools, containers push each other apart, and nodes outside a group are pushed out of its container. A last pass removes the remaining overlaps, deepest groups first, keeping `groupSpacing` around each container. Both engines do the same.
- **`layers`.** The whole graph shares one set of layers, so edges between groups point in the layer direction like the others. A group spans the layers from its first member to its last, and on each of them its members sit side by side, nested groups inside, with room for the padding and the label of every container. An edge that leaves a group goes out through the side its layers flow toward and comes into the next group from the other side: it crosses container borders only where it has to. Groups keep their members close in the direction of the layers, so a long chain makes a tall group.
- **`geo`.** Nodes keep their geographic place first. Containers that overlap, padding included, are then pushed apart, like the last pass of `force`.
- **`grid`, `rings` and `radial`.** Each group is laid out on its own with the same layout, from the deepest groups up. In the group above it, a group stands in as a single node the size of its container, and the nodes directly inside a group are laid out together first, as one more block. A grid of groups is a grid of blocks. The blocks are then pushed apart where they still overlap.
- **Fixed nodes and circles.** With `layers`, when some nodes do not move, because they have `x` and `y` in your data or were left out of the run, or when a container is a circle, the containers are pushed apart after the layout, only across the layers: every edge between two moving nodes still points forward. Fixed nodes keep their place and push the moving nodes and containers aside. Where fixed nodes leave too little room between them, some overlaps may remain.
- **Fixed members.** When two groups both hold a fixed node, their containers may be unable to move apart. Their moving nodes are then still pushed off each other and off the fixed nodes, while the containers may overlap.
- **Unfolding.** With a layout in the definition, a group that unfolds makes room for itself: the free nodes and containers it would cover glide out of the way over `transitions.layout`. Nodes it shows for the first time are laid out like new nodes. With `relayout: true` in the definition, a fold, an unfold, or a change of [`groups()` or `merge`](/docs/transformations#layout-after-a-change) runs the whole layout again instead.

On 50,000 nodes in about 400 groups nested three deep, the force layout takes about twice as long on the GPU (1 second instead of 0.5) and about 13% longer on the CPU (14 seconds instead of 12.5). See the [forces with groups](/examples/force-with-groups) example.

## When it runs

- **First nodes.** The layout runs on the first batch of nodes as soon as it arrives. Unless you passed `initialView`, the view keeps the graph framed while it settles, and once more at the end, as long as you do not pan or zoom.
- **New nodes.** With `force`, nodes added later are laid out alone. They start next to their placed neighbors and settle there, while the rest of the graph stays still. Nodes that arrive during a run join it. With `layers`, `grid`, `rings`, `radial` and `geo`, every free node is laid out again.
- **New layout.** A definition with another layout, or the same layout with other options, lays out every free node again on the next frame, starting from where the nodes are. Options are compared one by one, so calling `force({ edgeLength: 60 })` again in a render restarts nothing.
- **No layout.** `layout: null`, the default, turns it off. An automatic run in progress stops, and nodes stay where they are.

Since new nodes move alone, a graph that arrives in several batches does not look the same as one that arrives at once. Once the data is complete, `graph.layout.run()` lays out the whole graph again: the [live source](/examples/live-source) example does this when its stream ends, and [expand on double-click](/examples/expand-on-double-click) lets each new neighborhood settle alone.

The view follows only the first run. To frame every run, such as a new layout or new nodes, set `autoFit` in the `view` of the definition:

```ts
defineGraph({ marks, layout: force(), view: { autoFit: 'layouts' } })
```

The view then follows each run and frames its end, as long as you do not pan or zoom; the next `view.fit` starts it again. See [The first view](/docs/view#the-first-view). A run started from code can frame its result with [`fit`](#run-it-from-code) instead. The [force parameters](/examples/force-parameters) example lays out again and frames the graph each time a slider changes.

## Which nodes move

- **Positions from your data win.** Nodes whose mark has `x` and `y` channels, with finite values, never move. They still push and pull the others, so free nodes settle around them. A node whose `x` or `y` is `null` is free.
- **Dragging pins.** A node dragged during a run stays where you drop it, and the others settle around it. `graph.positions.set` pins its nodes the same way. The pin lasts until the end of the run.

To keep a node in place for good, give it coordinates in your data. See the [fixed nodes among free ones](/examples/fixed-and-free-nodes) example.

## Run it from code

`graph.layout` starts and stops runs.

```ts
const completed = await graph.layout.run()

await graph.layout.run(undefined, { keys: graph.selection.get().nodes })

await graph.layout.run(force({ edgeLength: 100 }))

await graph.layout.run(grid(), { fit: true, duration: 600 })

graph.layout.stop()
```

- `run()` lays out every free node with the layout of the definition, from the current positions. Pending data changes are applied first.
- `keys` limits the run to these nodes. The others stay still and act as anchors. A run on part of the graph starts with less energy and without the pull to the center, so the moved nodes stay near the rest.
- A layout passed to `run` is used for this run only. The definition keeps its own.
- `fit` frames the result. With `true`, the view fits every node; pass [fit options](/docs/view#fit) to frame some `nodes` or `edges`, or for padding or a duration. It aims at the final positions, so the view moves while the nodes do.
- The promise resolves to `true` when the run ends, and to `false` when it is stopped, replaced by another run, or when the graph is destroyed. It rejects when neither the call nor the definition has a layout.
- `stop()` ends the current run and leaves every node where it is.

The [drag to pin](/examples/drag-to-pin) example runs the layout again around the nodes you drag.

## Glide to the result

A layout that reports its result at once, without progress, such as `layers`, `grid`, `rings`, `radial` and `geo`, does not make nodes jump: they glide from where they are to where they go. The run, and its promise, end when they arrive.

The glide lasts `transitions.layout` milliseconds, 400 by default. `duration` in the run options overrides it for one run, and `0` places nodes at once.

```ts
defineGraph({ marks, layout: grid(), transitions: { layout: 600 } })

await graph.layout.run(rings(), { duration: 0 })
```

Dragged nodes and nodes with `x` and `y` in your data do not glide. `stop()` during the glide leaves nodes where they are at that moment.

## Follow the progress

The store holds the status of the current run, and two events frame it.

```ts tab="Vanilla" tab-group="framework"
graph.store.subscribe(() => {
  const { running, progress } = graph.store.get().layout
  bar.hidden = !running
  bar.value = progress
})

graph.on('layoutend', ({ name, completed }) => {
  console.log(name, completed ? 'done' : 'stopped')
})
```

```tsx tab="React" tab-group="framework"
import { useGraphState } from '@bruno00o/graph/react'

function LayoutProgress() {
  const { running, progress } = useGraphState((state) => state.layout)
  return running ? <progress value={progress} /> : null
}

<Graph definition={definition} ariaLabel="Sample graph" onLayoutEnd={({ completed }) => setSettled(completed)}>
  <LayoutProgress />
</Graph>
```

| Name | Value |
| --- | --- |
| `state.layout.running` | `true` while a run is in progress |
| `state.layout.progress` | From 0 to 1 |
| `layoutstart` | `{ name }`, when a run starts |
| `layoutend` | `{ name, completed }`, when a run ends or stops |

Nodes that arrive during a run join it without a new `layoutstart`.

## Save the result

When a run ends, `positionchange` fires with the origin `'layout'` and the positions of the nodes it moved, after the glide if there is one. A stopped run does not emit it.

[`persistPositions`](/docs/tanstack-db) writes these positions to your collection, as it does for a drag. The layout then becomes data, shared with every client that reads the collection. When the node mark reads `x` and `y` from it, those nodes now have coordinates and later runs leave them in place. To save only what users move by hand, filter on the origin.

```ts
graph.on('positionchange', ({ origin, positions }) => {
  if (origin !== 'layout') save(positions)
})
```

To keep a result without a collection, take `graph.positions.snapshot()` once the run ends and give it back to `positions.set` later. See [Save and restore](/docs/positions#save-and-restore).

## Force options

```ts
force({ edgeLength: 40, repulsion: 80, gravity: 0.04, spacing: 6, steps: 300, engine: 'auto', multilevel: 'auto' })
```

Every option, with its default, is listed in [`ForceOptions`](/docs/api/force#options).

A negative or non-finite value falls back to its default. The [force parameters](/examples/force-parameters) example sets `edgeLength`, `repulsion`, `gravity` and `spacing` with sliders.

## Engines

`'auto'` uses the GPU from 2,000 nodes, and the CPU below or when WebGL runs in software, where the CPU engine is several times faster. Both run in a Web Worker, so the page keeps panning and zooming while the layout runs.

- **CPU.** Repulsion is approximated with a quadtree, collisions are tested on a grid. The same graph and the same positions always give the same result.
- **GPU.** The same forces run in WebGL2 on an `OffscreenCanvas` inside the worker, with a density pyramid for repulsion. A last pass on the CPU removes the remaining overlaps. Results can differ by rounding from one run to the next.

The GPU engine needs WebGL2 in workers and the `EXT_color_buffer_float` and `EXT_float_blend` extensions. Without them, the CPU takes over. If the GPU context is lost during a run, the CPU resumes from the last positions.

<Callout title="Content security policy">
The worker is created from a `blob:` URL. When `Worker` is missing, when your policy refuses `worker-src blob:`, or when the worker fails, the simulation continues on the main thread in slices of 8 milliseconds, from where it was. Dragged nodes stay pinned.
</Callout>

## Large graphs

From 1,000 moving nodes, `force` works in levels. It merges each node with a neighbor, again and again, until a few nodes are left: each level has about half the nodes of the one below, and a merged node weighs what its members weigh. It lays out the smallest level in full, then starts each finer level from the one above, every node next to the node it was merged into, and lets it settle in a few steps. The last level is your graph.

<LiveExample slug="force-levels" />

Long shapes come out unfolded: a grid lies flat and a tree spreads its branches, where a single level folds them on themselves. On the CPU, a run is also several times faster: 80,000 nodes in communities settle in about 6 seconds instead of 21. On the GPU, the coarse levels run on the CPU inside the worker and the large ones on the GPU: 10,000 nodes take about 0.4 seconds instead of 0.25, 80,000 about as long as before, and a million about 7 seconds instead of 10.

- **When.** Runs that move at least half of the nodes: the first run, `layout.run()`, and new nodes that outnumber those already placed. Smaller arrivals settle around the placed nodes as before.
- **Option.** `multilevel: true` uses levels at any size, `false` never, and `'auto'`, the default, from 1,000 moving nodes.
- **Groups.** A graph with unfolded groups is laid out in a single level.
- **Fixed and pinned nodes.** Nodes with `x` and `y`, and nodes dragged during the run, keep their place at every level.
- **Progress.** The first snapshots show nodes gathered in small clusters, which open up level by level.
- **Same result.** On the CPU, the same graph and the same positions still give the same result.

<Callout title="A different result for large graphs">
Graphs with 1,000 moving nodes or more did not use levels before this option existed, so their layout looks different now. Pass `multilevel: false` to get the earlier result.
</Callout>

## Write your own layout

`layout` takes any object that implements the `Layout` port, exported as types from `@bruno00o/graph`.

```ts
import type { Layout } from '@bruno00o/graph'

export function circle(radius = 300): Layout {
  return {
    name: 'circle',
    options: { radius },
    start(graph, listener) {
      const xy = graph.xy.slice()
      const free: number[] = []
      for (let index = 0; index < graph.capacity; index++) {
        if (graph.movable[index] === 1) free.push(index)
      }
      free.forEach((index, at) => {
        const angle = (at / free.length) * Math.PI * 2
        xy[index * 2] = Math.cos(angle) * radius
        xy[index * 2 + 1] = Math.sin(angle) * radius
      })
      listener.end(xy)
      return { pin: () => {}, stop: () => {} }
    },
  }
}
```

- `start` receives a `LayoutGraph`: typed arrays indexed by the internal index of each node, with `alive`, `movable`, `xy`, `radius`, and `edges` as pairs of indices, loops left out. For a [box](/docs/marks#boxes), `radius` is the radius of the circle around it, and `extents` gives the half width and half height of every node when the graph has a box. `keys[index]` is the key of a node, and `datum(index)` the item it comes from. With unfolded groups, `groups` gives the group of each node, the padding of each container and the room its label takes outside it; a layout that ignores it still works, but it does not keep containers apart.
- It reports positions with `listener.progress(xy, progress)` as often as it likes, then `listener.end(xy)` once. Each array holds every node, and nodes that are not movable must keep their place. Ending without progress makes nodes glide to the result.
- It returns `pin(index, x, y)`, called when a node is dragged or set during the run, and `stop()`, after which it must not call the listener again.
- `name` and `options` decide whether a new definition lays out again: they are compared one by one.
- `incremental: false` lays out every free node again when nodes arrive, instead of the new ones only.

See [`force`](/docs/api/force), [`layers`, `grid`, `rings`, `radial`](/docs/api/layouts) and [`defineGraph`](/docs/api/define-graph#layout) for the types, and the [layout of your own](/examples/custom-layout) example.
