## Requirements

The graph needs WebGL2. Every current desktop and mobile browser has it. It is written against the minimum limits of the WebGL2 specification rather than the limits of a fast GPU, so it runs on any conformant device:

| Resource | Used at most | WebGL2 minimum |
| --- | --- | --- |
| Textures per vertex shader | 16 | 16 |
| Textures per fragment shader | 9 | 16 |
| Varying vectors | 8 | 15 |
| Uniform blocks per stage | 2 | 12 |
| Uniform block size | 3,088 bytes | 16,384 bytes |
| Vertex attributes | 7 | 16 |

A unit test compiles the budget of every shader variant against these minimums, so a change that would fail on a small GPU fails the build instead.

## Limits read at startup

The largest texture, drawing buffer and array texture differ from one device to the next: 2,048 pixels is the minimum, 4,096 is common on phones, 16,384 on desktops. The graph reads them when its WebGL context is created and keeps every texture within them. When something does not fit, the graph draws less rather than nothing, and warns once in development:

- **Nodes and edges.** Each is a row of a data texture 1,024 texels wide, so a device draws up to 1,024 times its largest texture size of each: 2,097,152 at the minimum, 16 million on most desktops. Elements past that are not drawn, nor the edges that touch them.
- **Canvas.** The drawing buffer is the CSS size times the device pixel ratio. When it would pass the largest drawing buffer, the pixel ratio is lowered until it fits: the graph is less sharp, never cut.
- **Lens.** The [lens](/docs/lens) radius shrinks to fit the drawing buffer.
- **Images.** The image atlas holds as many images as the device has array texture layers, 256 at most. Further images are neither loaded nor drawn until a stored image is no longer used.
- **Edge paths.** [Bundled](/docs/bundling) and [routed](/docs/routing) edges sample their paths more coarsely when the points would not fit, then draw the last edges straight.
- **Labels.** The glyph atlas grows up to the largest texture size, about 2,000 characters at the minimum, each weight and font counted apart. When it is full, it starts over with the characters of the labels on screen. If those do not fit either, the extra characters are not drawn and the atlas waits 8 frames before it starts over again.

## Optional extensions

The graph draws without any extension. A few make some features faster or tidier, and each has a fallback:

| Extension | Used for | Without it |
| --- | --- | --- |
| `EXT_color_buffer_float` and `EXT_float_blend` | The GPU engine of the [force layout](/docs/layout) | The layout runs on the CPU, in a worker |
| `WEBGL_lose_context` | Freeing a context as soon as a graph or an export is destroyed | The browser frees it later |
| `WEBGL_debug_renderer_info` | Recognizing a software renderer | The renderer name the browser reports is used |

Nothing else is needed: float textures are always read without filtering, and the lens, the minimap, exports and the edge layer cap only use core WebGL2.

## Context loss

The browser can take a WebGL context away at any time: the GPU process crashed, the driver updated, or too many pages hold a context. The graph then stops drawing and waits. When the browser gives the context back, the graph builds its renderer again from the scene it keeps on the CPU and draws the same picture: data, positions, view, selection, states, lens and theme are unchanged, and nothing is needed from you.

An export in progress when the context is lost rejects with an error: call it again.

On a [map](/docs/map), the context belongs to the map. MapLibre rebuilds its style once the context comes back, but cannot rebuild custom layers, and logs a warning saying so. The graph listens for the map's `webglcontextrestored` event and adds its layer back, so the warning can be ignored.

## Software rendering

Without a usable GPU, a browser either refuses WebGL or draws it on the CPU with a software rasterizer, as on some virtual machines, remote desktops and test runners. Chrome no longer falls back to one by itself. The graph recognizes a software renderer by its name and adapts:

- The canvas is drawn at one pixel per CSS pixel, whatever the device pixel ratio.
- The `'auto'` engine of the [force layout](/docs/layout) runs on the CPU: on a software renderer it is several times faster than the GPU engine.
- In development, a graph of more than 20,000 nodes and edges warns once.

What remains costs about 10 microseconds per node or edge drawn, at any canvas size. Measured in Chrome with its software rasterizer, while the view moves:

| Graph | Time per frame |
| --- | --- |
| 1,000 nodes and 1,800 edges | 40 ms |
| 10,000 nodes and 20,000 edges | 350 ms |
| 50,000 nodes and 100,000 edges | 1.8 s |

The first frame takes about 3 seconds more while the shaders compile, and the graph draws nothing at rest. Software rendering suits graphs of a few thousand elements; past that, filter or aggregate the data first.

## Tested browsers

Every pull request opens each example of this site and of the repository in Chromium, Firefox and WebKit, on Linux without a GPU, and a few of them again with the WebGL2 minimum limits. Each page must draw, pick the node under the pointer, select it on click and zoom on the wheel, with no error in the console.

- **Firefox on Linux** creates no WebGL context without a display server, even when headless. To test a page with a graph in headless Firefox on Linux, run it under a virtual display.
- **WebKit on Linux** has no WebGL2 in workers, so the [force layout](/docs/layout) runs on the CPU there.

## Device pixel ratio and size

The canvas follows the device pixel ratio, including when a window moves to a screen with another one. A resized graph is drawn again before the browser paints, so dragging a window edge never shows an empty frame. A container of 0 pixels is allowed; the graph warns once in development and draws nothing until it gets a size.

## Safari, Firefox and Chrome

The examples are checked in Chrome, Safari and Firefox on macOS with a hardware GPU, in light and dark themes, and draw the same picture in all three: nodes, edges, labels, layouts, the map and the globe, the lens, the minimap, the timeline and the exports. The force layout of 80,000 nodes on the GPU takes about the same time in each.

Each browser has its own way of reporting some input, and the graph reads them all:

| Input | Safari | Firefox | Chrome |
| --- | --- | --- | --- |
| Trackpad pinch | Gesture events with a scale, and wheel events with Ctrl | Wheel events with Ctrl | Wheel events with Ctrl |
| Touch pinch | Touch pointers, and gesture events | Touch pointers | Touch pointers |
| Wheel | Pixels | Pixels, or lines on some systems | Pixels |

- **Pinch in Safari.** The graph, the [minimap](/docs/minimap-and-legend) and the [timeline](/docs/time) zoom by the scale of the gesture, around the pointer, and prevent the gesture so that Safari does not zoom the page. The wheel events of the same pinch are ignored, so the zoom is never applied twice. A touch pinch on iOS is read from the pointers, as in other browsers.
- **Wheel lines and pages.** Deltas counted in lines are converted at 16 pixels a line, and deltas counted in pages at the size of the element, in the graph, the minimap and the timeline.

The work done off the main thread uses workers and `OffscreenCanvas`, which the three browsers support. Each has a fallback:

| Feature | In a worker | Without |
| --- | --- | --- |
| GPU engine of the force layout | WebGL2 on an `OffscreenCanvas` | The layout runs on the CPU |
| CPU engine of the force layout, edge bundling | Plain worker | Runs on the main thread in slices |
| Minimap | 2D `OffscreenCanvas`, each frame sent to the page as an `ImageBitmap` | Drawn on the page |

Workers are started from a `blob:` URL: a content security policy without `worker-src blob:` turns them all to their fallback. PNG export compresses with `CompressionStream`, available in every current browser.

Known limits:

- On macOS, Safari can still open its tab overview on a pinch that also rotates, even though the graph prevents the gesture.
- In Firefox, the console can report that a texture is initialized lazily the first time it is drawn. This is informational: the texture is filled before use.
- In Firefox, the console reports `WebGL context was lost.` each time a graph, an export or the GPU layout frees its context on purpose, for instance when React mounts a component twice in development. Nothing is lost: see [Context loss](#context-loss) for a real one.

## Testing on a small device

The development examples take a `caps` query parameter that makes the browser report the WebGL2 minimum limits and hide every optional extension, so a fast machine behaves like the smallest conformant device. See the repository README.
