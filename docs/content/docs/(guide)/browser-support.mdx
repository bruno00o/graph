## Requirements

The graph needs WebGL2. Every current desktop and mobile browser has it. It is written against the minimum limits of the WebGL2 specification rather than the limits of a fast GPU, so it runs on any conformant device:

| Resource | Used at most | WebGL2 minimum |
| --- | --- | --- |
| Textures per vertex shader | 16 | 16 |
| Textures per fragment shader | 9 | 16 |
| Varying vectors | 8 | 15 |
| Uniform blocks per stage | 2 | 12 |
| Uniform block size | 3,088 bytes | 16,384 bytes |
| Vertex attributes | 7 | 16 |

A unit test compiles the budget of every shader variant against these minimums, so a change that would fail on a small GPU fails the build instead.

## Limits read at startup

The largest texture, drawing buffer and array texture differ from one device to the next: 2,048 pixels is the minimum, 4,096 is common on phones, 16,384 on desktops. The graph reads them when its WebGL context is created and keeps every texture within them. When something does not fit, the graph draws less rather than nothing, and warns once in development:

- **Nodes and edges.** Each is a row of a data texture 1,024 texels wide, so a device draws up to 1,024 times its largest texture size of each: 2,097,152 at the minimum, 16 million on most desktops. Elements past that are not drawn, nor the edges that touch them.
- **Canvas.** The drawing buffer is the CSS size times the device pixel ratio. When it would pass the largest drawing buffer, the pixel ratio is lowered until it fits: the graph is less sharp, never cut.
- **Lens.** The [lens](/docs/lens) radius shrinks to fit the drawing buffer.
- **Images.** The image atlas holds as many images as the device has array texture layers, 256 at most. Further images are neither loaded nor drawn until a stored image is no longer used.
- **Edge paths.** [Bundled](/docs/bundling) and [routed](/docs/routing) edges sample their paths more coarsely when the points would not fit, then draw the last edges straight.
- **Labels.** The glyph atlas grows up to the largest texture size, about 2,000 characters at the minimum, each weight and font counted apart. When it is full, it starts over with the characters of the labels on screen. If those do not fit either, the extra characters are not drawn and the atlas waits 8 frames before it starts over again.

## Optional extensions

The graph draws without any extension. A few make some features faster or tidier, and each has a fallback:

| Extension | Used for | Without it |
| --- | --- | --- |
| `EXT_color_buffer_float` and `EXT_float_blend` | The GPU engine of the [force layout](/docs/layout) | The layout runs on the CPU, in a worker |
| `WEBGL_lose_context` | Freeing a context as soon as a graph or an export is destroyed, and when a graph is [suspended](#many-graphs-on-a-page) | The browser frees it later, and a suspended graph keeps its context: it only frees its textures and buffers |
| `WEBGL_debug_renderer_info` | Recognizing a software renderer | The renderer name the browser reports is used |

Nothing else is needed: float textures are always read without filtering, and the lens, the minimap, exports and the edge layer cap only use core WebGL2.

## Context loss

The browser can take a WebGL context away at any time: the GPU process crashed, the driver updated, or too many pages hold a context. The graph then stops drawing and waits, as when [suspended](/docs/api/graph-instance#suspend): data and live sources, layouts, the view and its animations, controlled requests and the companions go on, and `graph.drawn()` waits for the context. When the browser gives the context back, the graph builds its renderer again from the scene it keeps on the CPU and draws the same picture: data, positions, view, selection, states, lens and theme are unchanged, and nothing is needed from you.

An export in progress when the context is lost rejects with an error: call it again.

On a [map](/docs/map), the context belongs to the map. MapLibre rebuilds its style once the context comes back, but cannot rebuild custom layers, and logs a warning saying so. The graph listens for the map's `webglcontextrestored` event and adds its layer back, so the warning can be ignored.

## Many graphs on a page

A page holds at most 16 WebGL contexts in Chrome and Safari, and more in Firefox. Each graph takes one for its canvas, and a PNG export one more while it draws. The minimap draws without WebGL, and the GPU engine of the [force layout](/docs/layout) takes its context in a worker, which does not count. Past the limit, the browser takes the oldest context away and says so in the console: that graph stops drawing and waits for its context, as after any [context loss](#context-loss), but Chrome and Safari do not give back a context taken for this reason.

With more graphs than that, [suspend](/docs/api/graph-instance#suspend) those out of sight and resume them as they come back. A suspended graph gives its context back to the browser, shows a copy of its last frame, and keeps everything else; once resumed, it takes a context again and draws the graph as it is now. On a page of 20 graphs of 400 nodes, with 8 resumed at a time, scrolling through every graph took no context away from a shown graph in Chrome, Firefox or Safari, and a graph drew again 130 to 280 ms after it came into sight, as a median, several graphs resuming at once. Mount the graphs that start out of sight with `suspended: true`: they create no context until they resume. The copy of the last frame costs about 7.7 MB per suspended graph of 800 × 600 CSS pixels at a ratio of 2: `keepFrame: false` keeps none, and the page then shows an empty box for the 60 to 120 ms a graph takes to draw again.

A graph that the browser took a context from, because the page held more than 16, stays empty in Chrome and Safari. `resume()` gets a context back for it, suspended or not: the graph asks the browser to restore it and draws again, in Chrome and Safari alike, at the price of the oldest context of another graph. Call it on the graphs that come into sight.

Safari still counts the context of a suspended graph. Before it takes a context, a graph uses every other context of the page that is still drawing, so that Safari takes away one of a suspended graph, which is already free. With more than 16 graphs on the page, the console then reports `There are too many active WebGL contexts on this page, the oldest context will be lost.` and `WebGL: INVALID_OPERATION: loseContext: context already lost`: no shown graph loses its context, and the suspended graph gets one back when it resumes.

## Software rendering

Without a usable GPU, a browser either refuses WebGL or draws it on the CPU with a software rasterizer, as on some virtual machines, remote desktops and test runners. Chrome no longer falls back to one by itself. The graph recognizes a software renderer by its name and adapts:

- **Plain triangles instead of instances.** A software rasterizer pays a fixed cost for each instance of an instanced draw, about 6 microseconds in Chrome, whatever its size. In software, the graph repeats the data of each node, edge, label and badge for every corner of its shape, and draws plain triangles, tens of times cheaper per element. When no edge has an arrow at one end, it also leaves out the triangles that join that arrow to the line. The picture is the same, pixel for pixel. The vertex buffers take more memory, counted in the texture memory of the [devtools](/docs/devtools). Bundled and routed edges, edges with waypoints, shapes and hulls keep their instanced draws. The code of plain triangles comes in a chunk of its own, loaded only once WebGL turns out to run in software, so a browser with a GPU downloads nothing more. The graph waits for that chunk before its first frame, and [`drawn()`](/docs/api/graph-instance#drawn) with it; should it fail to load, the graph draws instances and warns in development.
- **Programs prepared when first used.** With a GPU, the graph draws each program once at startup, so that the first labels do not stall a later frame. In software it does not, and the program of node labels and badges leaves out the code of edge labels: the first frame comes about 2 seconds earlier.
- **One pixel per CSS pixel.** The `pixelRatio` option of [`defineGraph`](/docs/api/define-graph#pixel-ratio), `'auto'` by default, draws the canvas at one pixel per CSS pixel when WebGL runs in software, whatever the device pixel ratio: the graph is less sharp on a high density screen. `'device'` keeps the device pixel ratio, and a number sets the ratio with any renderer, `1` to spend less on a weak GPU.
- The `'auto'` engine of the [force layout](/docs/layout) runs on the CPU: on a software renderer it is several times faster than the GPU engine.
- In development, a graph of more than 20,000 nodes and edges warns once.

Nothing else is left out: labels, arrows, dashes, halos, the selection and the hover look the same as with a GPU. The [devtools](/docs/devtools) panel shows whether WebGL draws on a GPU or in software, and the pixel ratio the graph draws at, with its reason.

```ts
const definition = defineGraph({
  marks: [edges(links, { source: 'from', target: 'to' }), nodes(items, { label: 'name' })],
  pixelRatio: 'device',
})
```

A frame costs about the same at rest, while the view moves and on hover. It grows with the number of nodes and edges drawn, through the triangles the rasterizer sets up, more than with the size of the canvas. Software rasterizers spread a frame over the cores of the processor, so the time depends on how many the browser gets. Measured while the view moves and on hover, the whole graph in view on a canvas of 1280 × 800 pixels, with arrows and labels, in Chrome on macOS with 12 cores and in Chrome and Firefox in a Linux container limited to 4 cores of the same machine:

| Graph | Chrome, 12 cores | Chrome, 4 cores | Firefox, 4 cores |
| --- | --- | --- | --- |
| 1,000 nodes and 2,000 edges | 6 ms | 18 ms | 17 ms |
| 10,000 nodes and 20,000 edges | 32 to 43 ms | 190 to 200 ms | 100 to 105 ms |
| 50,000 nodes and 100,000 edges | 150 to 205 ms | 0.9 to 1.1 s | 480 to 530 ms |

Firefox on Linux draws WebGL with llvmpipe, another software rasterizer, which pays no fixed cost per instance: with few cores, it draws large graphs faster than Chrome. WebKit on Linux draws with llvmpipe too, but reports a GPU, so the graph keeps the device pixel ratio there unless `pixelRatio` sets one; its frames take about as long as in Firefox.

The first frame takes 2 to 2.5 seconds in Chrome from 1,000 to 50,000 nodes, and about 1 second in Firefox, most of it to create the WebGL context and prepare the programs, and the graph draws nothing at rest. Where the browser composes the page without a GPU too, as Chrome does on Linux, the page waits for each frame of the graph to be drawn before it answers again, so a frame of a large graph freezes the page for its whole time. With any renderer, the graph measures how long its frames take, and a move of the view, of nodes or of edge shapes goes straight to its end when the last frames took longer than what is left of it: a click that frames a node costs one frame, not several. Software rendering suits graphs of a few tens of thousands of elements on a desktop processor, and fewer on a virtual machine of a few cores; past that, filter or aggregate the data first.

## Tested browsers

Every pull request opens each example of this site and of the repository in Chromium, Firefox and WebKit, on Linux without a GPU, and a few of them again with the WebGL2 minimum limits. Each page must draw, pick the node under the pointer, select it on click and zoom on the wheel, with no error in the console.

- **Firefox on Linux** creates no WebGL context without a display server, even when headless. To test a page with a graph in headless Firefox on Linux, run it under a virtual display.
- **WebKit on Linux** has no WebGL2 in workers, so the [force layout](/docs/layout) runs on the CPU there.

## Without a browser

[`createGraph`](/docs/api/create-graph) of `@bruno00o/graph/headless` makes a graph that needs neither a browser nor WebGL: it reads no DOM global and creates no worker. It is tested in Node 24, and uses no API that Deno, Bun or a web worker lack. Its layouts, edge bundling and edge routing run on the calling thread, in slices of 50 ms. A test suite runs it in Node with every global of the DOM replaced by a getter that throws, so that a change that would reach for the page fails the build. Such a graph exports SVG, draw.io and Visio files, not PNG: [Server-side extracts](/docs/server-side-extracts) rasterizes the SVG with resvg.

## Device pixel ratio and size

The canvas follows the device pixel ratio, including when a window moves to a screen with another one, unless the [`pixelRatio`](/docs/api/define-graph#pixel-ratio) of the definition sets another; the largest drawing buffer of the device caps it. A resized graph is drawn again before the browser paints, so dragging a window edge never shows an empty frame. A container of 0 pixels is allowed; the graph warns once in development and draws nothing until it gets a size.

## Safari, Firefox and Chrome

The examples are checked in Chrome, Safari and Firefox on macOS with a hardware GPU, in light and dark themes, and draw the same picture in all three: nodes, edges, labels, layouts, the map and the globe, the lens, the minimap, the timeline and the exports. The force layout of 80,000 nodes on the GPU takes about the same time in each.

Each browser has its own way of reporting some input, and the graph reads them all:

| Input | Safari | Firefox | Chrome |
| --- | --- | --- | --- |
| Trackpad pinch | Gesture events with a scale, and wheel events with Ctrl | Wheel events with Ctrl | Wheel events with Ctrl |
| Touch pinch | Touch pointers, and gesture events | Touch pointers | Touch pointers |
| Wheel | Pixels | Pixels, or lines on some systems | Pixels |

- **Pinch in Safari.** The graph, the [minimap](/docs/minimap-and-legend) and the [timeline](/docs/time) zoom by the scale of the gesture, around the pointer, and prevent the gesture so that Safari does not zoom the page. The wheel events of the same pinch are ignored, so the zoom is never applied twice. A touch pinch on iOS is read from the pointers, as in other browsers.
- **Wheel lines and pages.** Deltas counted in lines are converted at 16 pixels a line, and deltas counted in pages at the size of the element, in the graph, the minimap and the timeline.
- **Wheel notches.** A notch of a mouse wheel [glides](/docs/interaction#wheel-glide), a trackpad scroll moves the view at once. Chrome and Safari report the notches of a macOS mouse as fixed-point line steps, and Chrome and Firefox report whole wheel ticks on Windows and Linux. Firefox on macOS reports mouse notches in pixels, like a trackpad scroll, so they do not glide there.

The work done off the main thread uses workers and `OffscreenCanvas`, which the three browsers support. Each has a fallback:

| Feature | In a worker | Without |
| --- | --- | --- |
| GPU engine of the force layout | WebGL2 on an `OffscreenCanvas` | The layout runs on the CPU |
| CPU engine of the force layout, edge bundling | Plain worker | Runs on the main thread in slices |
| Triangulation of large shape batches | Plain workers | Runs on the main thread in slices |
| Minimap | 2D `OffscreenCanvas`, each frame sent to the page as an `ImageBitmap` | Drawn on the page |

Workers are started from a `blob:` URL: a content security policy without `worker-src blob:` turns them all to their fallback. PNG export compresses with `CompressionStream`, available in every current browser.

Known limits:

- On macOS, Safari can still open its tab overview on a pinch that also rotates, even though the graph prevents the gesture.
- In Firefox, the console can report that a texture is initialized lazily the first time it is drawn. This is informational: the texture is filled before use.
- In Firefox, the console reports `WebGL context was lost.` each time a graph, an export or the GPU layout frees its context on purpose, for instance when React mounts a component twice in development, or when a graph is suspended. Nothing is lost: see [Context loss](#context-loss) for a real one.

## Testing on a small device

The development examples take a `caps` query parameter that makes the browser report the WebGL2 minimum limits and hide every optional extension, so a fast machine behaves like the smallest conformant device. See the repository README.
