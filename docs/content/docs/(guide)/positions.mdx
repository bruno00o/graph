## Initial placement

A node gets its first position in this order:

1. From the `x` and `y` channels, when the mark has them, or else from `longitude` and `latitude`.
2. Near its neighbors that are already placed, on a ring around them. A node that arrives while you explore appears next to what it connects to.
3. Otherwise on a spiral around the origin. A first batch without coordinates starts as a compact disc.

When some nodes are placed by their data, a node without coordinates goes near its placed neighbors from the first batch on, and the walk goes on through the nodes it places, so a chain of nodes without coordinates hangs from the placed node it connects to. A node with no placed neighbor at all, and the nodes that hang from it, start next to the node placed by its data that is nearest the middle of the others, not at the origin. The ring is sized in pixels at the zoom of the moment for a node sized with `units: 'screen'`, such as nodes on a [map](/docs/map), and in world units otherwise. A graph where every node, or no node, is placed by its data is placed as described above.

With a layout in the definition, nodes without `x` and `y` then move to the place it computes: the first batch as a whole, later nodes next to their neighbors. See [Layouts](/docs/layout).

## Positions from your data

`x` and `y` are channels like the others: a field or a function, in world units. When an update changes them, the node moves there.

```ts
const definition = defineGraph({
  marks: [nodes(items, { label: 'label', x: 'x', y: 'y' })],
  transitions: { positions: 200 },
})
```

The move is animated over `transitions.positions` milliseconds, 120 by default, and 0 with `prefers-reduced-motion`. Updates spaced by a paced write stay smooth.

A node only moves when its own `x` or `y` value changes, or its `longitude` or `latitude`. A node dragged by the user does not jump back when another field of its data changes, and incoming updates are ignored while the user is dragging it.

## Longitude and latitude

`longitude` and `latitude`, in degrees, place a node with Web Mercator, the projection of web maps. The world spans 512 units, from longitude -180 at `x` 0 to longitude 180 at `x` 512, and from latitude 85.05 at `y` 0 to latitude -85.05 at `y` 512. Nodes placed this way default to `units: 'screen'`, so their size does not change with the zoom.

```ts
nodes(places, { longitude: 'lng', latitude: 'lat', label: 'name' })
```

`geoToWorld` and `worldToGeo` convert between degrees and world units, for example to read where the user clicked. Edges between such nodes can follow [great circles](/docs/map#great-circles) with `geodesic`. To draw the nodes over a basemap, flat or on a globe, see [Map](/docs/map). Nodes placed this way never move, even when they overlap: to move apart on screen those at the very same place, see [Nodes at one place](#nodes-at-one-place); to place them by their coordinates and keep every node apart, use the [`geo` layout](/docs/layout#geography) instead.

## Nodes at one place

Nodes that the data places at the very same point draw on top of each other. `spread` in the definition moves them apart around that point, so that each one can be seen, hovered and dragged:

```ts
const definition = defineGraph({
  marks: [nodes(places, { longitude: 'lng', latitude: 'lat', label: 'name' })],
  spread: { gap: 4 },
})
```

<api-table path="index.ts" name="SpreadOptions" />

- `spread` is off by default; `true` takes a `gap` of 4. Nodes at the same point sit on a ring around it, or on a spiral past six. Nodes at different points never move, even when they touch: only the exact same `x` and `y`, or `longitude` and `latitude`, count.
- Only the drawn position moves, as for the [children of a group](/docs/groups#spread-children): `graph.positions.get` gives where a node is drawn, no `positionchange` is emitted, so `persistPositions` never writes a spread position, and a layout never moves a spread node.
- Nodes sized with `units: 'screen'`, such as nodes placed by `longitude` and `latitude`, keep their gap in pixels at every zoom; nodes in world units are spread once and never move as you zoom.
- It applies to the nodes outside groups that are placed by their data. The children of an unfolded group follow the `spread` of their [container](/docs/groups#spread-children) instead.
- A node you drag, or place with `graph.positions.set`, leaves the others and stays where you put it; they close ranks. It joins them again when its data moves, or with `graph.positions.reset`.
- Nodes glide out of their place over `transitions.layout`, or appear at once with reduced motion.

## Move nodes from code

```ts
graph.positions.get('n1')
graph.positions.set([['n1', { x: 0, y: 0 }], ['n2', { x: 80, y: 0 }]], { duration: 300 })
graph.positions.set(new Map([['n3', { x: 40, y: 60 }]]))
```

`set` takes any iterable of `[key, point]` pairs; a `Map` works. Without a duration, the nodes move at once. A pair whose `x` or `y` is not a finite number, such as `NaN` or a missing value, is skipped with a warning in development: its node stays where it is, and the other pairs apply.

## Put nodes back

`positions.reset` puts nodes back where their data places them, which a drag or `set` has changed: the `x` and `y` channels, or `longitude` and `latitude`. It animates over `transitions.positions`, or over the `duration` you pass, for the keys you give or for every node without them. On a map, where the camera is the only other way to restore a view, it is the way to undo what the user dragged.

```ts
graph.positions.reset()
graph.positions.reset(['n1', 'n2'], { duration: 600 })
```

A node whose data has no position, because a layout places it, stays where it is: the data has nothing to put it back to. A node that is already where its data says does not move, and does not appear in `positionchange`. The [reset positions](/examples/reset-positions) example puts back every node, or only the selection.

## Save and restore

`positions.snapshot()` reads every node at once, in a new `Map` from key to point that `set` takes back as is. It holds every node of the data, those hidden in folded groups included.

```ts
const saved = graph.positions.snapshot()
localStorage.setItem('positions', JSON.stringify([...saved]))

graph.positions.set(new Map(JSON.parse(localStorage.getItem('positions') ?? '[]')), {
  duration: 400,
})
```

A node that glides, after `set` with a duration, after a layout result or toward new `x` and `y` values, is read where it is going, so a snapshot taken mid-glide is the layout you will see. `snapshot({ settled: false })` reads where nodes are drawn now, as `get` does.

To restore a snapshot when you mount a graph again, use `initialPositions` instead of `set`: see [Restore at mount](#restore-at-mount).

Examples: [save and restore positions](/examples/save-positions) takes a snapshot and sets it back, and [snap to a grid](/examples/snap-to-grid) moves a dropped node to the nearest grid point.

## Restore at mount

An app that mounts a graph again, after a route change, a remount in React or a switch between a plain graph and a map, wants the nodes back where they were. Pass the snapshot as `initialPositions`, to `mountGraph`, `mountMapGraph`, `<Graph>` or `<MapGraph>`. It takes what `positions.snapshot()` returns, and what `positions.set` accepts.

```ts
const saved = graph.positions.snapshot()
graph.destroy()

const again = mountGraph(container, {
  definition,
  ariaLabel: 'Sample graph',
  initialPositions: saved,
})
```

Calling `positions.set` after the mount costs more: it applies the pending data first, which starts the first layout run on every node, then pins the nodes, and emits `positionchange`. `initialPositions` places the nodes while the data arrives:

- A node with an entry is drawn there and counts as laid out. No layout runs for it, `layoutstart` and `layoutend` do not fire for it, `positionchange` does not fire, and [`persistPositions`](/docs/tanstack-db) has nothing to write. It is not pinned: a later `layout.run` or a new layout moves it like any other free node.
- A node without an entry is new to the graph. The layout places it as an arrival, next to its placed neighbors, while the placed nodes stay still. With `force`, that is the run of [new nodes](/docs/layout#when-it-runs); with `layers`, `grid`, `rings`, `radial` and `geo`, which lay every free node out again when nodes arrive, the placed nodes move too.
- Positions from your data win: a node with `x` and `y`, or `longitude` and `latitude`, ignores its entry.
- With `autoFit: 'first'`, the first frame fits the restored nodes. It does not wait for a layout, and `initialView` still wins.
- An entry whose `x` or `y` is not finite is skipped, with a warning in development. An entry whose key never arrives does nothing.

The entries serve the nodes of the first data: those that arrive while a live source with a `status` is loading, or in the first batch of any other data. Then they are dropped, so a node that arrives much later is a new node. With `waitForData`, nodes that have no entry wait for the data to load and are then laid out together, while the nodes with an entry are drawn at once.

Nodes hidden in a folded group keep their restored place, and appear there when the group opens. A folded group keeps its own entry. Children of a group that [spread](/docs/groups#spread-children) stay where the snapshot puts them, as with `set`: it already holds the spread. A snapshot holds the positions of one surface, the one the graph is on: positions read on a map are in the world units of the map, so give them back to a map graph, and those of a plain graph to a plain one. A graph moved with [`surface`](/docs/map#with-and-without-a-map) keeps the positions of each side by itself.

The [layout in a Web Worker](/examples/layout-in-a-worker) example lays a graph out in a worker, then mounts it from the positions the worker sends back.

## Save a whole arrangement

An app can let the user save the arrangement of a view on request, as one record of its own: one value that holds every node, instead of one row per node as [`persistPositions`](/docs/tanstack-db#write-positions-back) writes. Take the record from `positions.snapshot()`, and give it back at the next mount with `initialPositions`, or to a live graph with `positions.set`.

```ts
import { defineGraph, mountGraph, nodes } from '@bruno00o/graph'
import type { Key, Point } from '@bruno00o/graph'

interface Item {
  id: string
  label: string
}
declare const items: Item[]
declare const container: HTMLElement
declare function loadArrangement(): [Key, Point][] | undefined
declare function storeArrangement(entries: [Key, Point][]): void

const definition = defineGraph({ marks: [nodes(items, { label: 'label' })] })

const graph = mountGraph(container, {
  definition,
  ariaLabel: 'Sample graph',
  initialPositions: loadArrangement(),
})

function save() {
  storeArrangement([...graph.positions.snapshot()])
}
```

`initialPositions` is read once, and `undefined` means no entries. To go back to a saved arrangement on a graph that is already mounted, pass the record to `positions.set`, with a `duration` to glide.

```ts
function restore(entries: Iterable<readonly [Key, Point]>) {
  graph.positions.set(entries, { duration: 400 })
}
```

### Keys that no longer exist

A record outlives the data. An entry whose key is not a node of the graph is ignored by both ways of restoring, without a warning, and the other entries apply. A node that has no entry is a new node: the layout places it next to its placed neighbors, or it starts on the spiral without a layout. A snapshot is complete, so the next save drops the stale entries by itself. To clean a record you hold, keep the entries whose key `positions.get` knows.

```ts
function pruned(entries: [Key, Point][]) {
  return entries.filter(([key]) => graph.positions.get(key) !== undefined)
}
```

### Tell user moves from replayed ones

`positionchange` says where a move comes from in its `origin`: `'drag'` for a node the user dragged, and for the nodes that followed it with [`drag: 'elastic'`](/docs/interaction#let-the-neighbors-follow), once they are calm, `'layout'` for a layout run that ended, and `'api'` for `positions.set` and `positions.reset`. Restoring through `initialPositions` emits nothing. Restoring through `set` emits `'api'`, as does any other call of yours, so a flag around your own replay keeps it from counting as an edit.

```ts
let restoring = false
let unsaved = false

graph.on('positionchange', ({ origin }) => {
  if (origin === 'api' && restoring) return
  unsaved = true
})

function replay(entries: Iterable<readonly [Key, Point]>) {
  restoring = true
  graph.positions.set(entries)
  restoring = false
  unsaved = false
}
```

The event fires inside `set`, so the flag only has to span that call. A layout result is an edit too: the arrangement changed, and `'layout'` marks it unsaved until the next save.

### On a map

A snapshot is in the world units of its surface, so on a map graph it is a record of the map. The snapshot of a plain graph does not fit a map graph, and the other way round. When the nodes are placed by `longitude` and `latitude` and the record has to survive a change of surface, save degrees: `worldToGeo` on each point at save time, `geoToWorld` at restore time. `worldToGeo` does not wrap the longitude, so a node dragged past the antimeridian comes back outside -180 to 180 and you wrap it. The `geo` of `positionchange` is already wrapped, and only exists on a map.

```ts
import { geoToWorld, worldToGeo } from '@bruno00o/graph'
import type { GeoPoint, Key, Point } from '@bruno00o/graph'

function wrap(longitude: number) {
  return ((((longitude + 180) % 360) + 360) % 360) - 180
}

function degrees(entries: Iterable<readonly [Key, Point]>) {
  return [...entries].map(([key, point]) => {
    const { longitude, latitude } = worldToGeo(point)
    return [key, { longitude: wrap(longitude), latitude }] as const
  })
}

function world(entries: Iterable<readonly [Key, GeoPoint]>) {
  return [...entries].map(([key, geo]) => [key, geoToWorld(geo)] as const)
}
```

See [With and without a map](/docs/map#with-and-without-a-map) for nodes placed by coordinates.

## Listen to moves

`positionchange` fires when nodes are moved by a drag, by `positions.set`, or by a layout run that ended, with their target positions. Its `origin` is `'drag'`, `'api'` or `'layout'`. Moves that come from your data do not emit it, so writing the positions back to the data never loops.

During a drag, it fires on every move of the pointer. To save once per drag, listen to `dragend` instead, or pace your writes.

```ts
graph.on('positionchange', ({ origin, positions }) => {
  if (origin !== 'drag') save(positions)
})

graph.on('dragend', ({ keys }) => {
  save(new Map(keys.map((key) => [key, graph.positions.get(key)])))
})
```

On a map, `positionchange` also carries `geo`: the same moved nodes as longitude and latitude in degrees, the longitude from -180 up to 180, so a drag across the antimeridian still gives a valid coordinate. Off a map, it is absent: convert with `worldToGeo` when your nodes are placed by coordinates.

```ts
graph.on('positionchange', ({ geo }) => {
  for (const [key, { longitude, latitude }] of geo ?? []) save(key, longitude, latitude)
})
```

To write positions to a TanStack DB collection, use [`persistPositions`](/docs/tanstack-db), which can write degrees.
